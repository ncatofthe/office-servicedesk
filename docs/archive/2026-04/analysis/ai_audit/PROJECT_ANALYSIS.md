# Project Analysis & Delivery Plan (Task Manager)
Дата: 2026-04-04
Автор: AI CTO / AI EM

## 1. Project Overview
- Назначение: fullstack система для управления задачами с ролями, ревью и выплатами; ключевой поток — задача → исполнители → ревью → оплата → отчётность.
- Основные компоненты: REST API (Express + Prisma/PostgreSQL), SPA (React 19 + Vite + Tailwind), seed-данные, вспомогательные скрипты.
- Технологический стек: Node.js 20, Express 5, Prisma 5, PostgreSQL; JWT + bcrypt; multer для файлов; frontend — React/TS, Zustand, react-router v7, Recharts, @dnd-kit.
- Уровень зрелости: функциональный прототип (QA-предрелиз). Есть рабочие фичи и seed, но нет тестов/CI, наблюдаемости и единых контрактов; часть валидации и RBAC неполная.

## 2. As-Is Architecture
- Тип: монолитный REST API + SPA. Вертикали разделены по папкам (routes/controllers/services) без доменной модуляризации.
- Бэкенд модули: auth, users, tasks (комментарии/файлы/история), reviews (approval + платеж), notifications, finance (accounts/transactions), dashboard, reports.
- Данные: Prisma schema → PostgreSQL. Файлы хранятся на диске (`/uploads`) с путями в БД.
- Интеграции: нет внешних сервисов; rate-limit и аудит — in-memory/console.
- Проблемы связности: дубли DTO между FE/BE, нет shared контрактов; проверка прав разбросана; единый error-формат отсутствует; нет API версионирования.

## 3. Technical Audit
- Качество кода: читаемые контроллеры/сервисы, но backend на JS без типов; частичная валидация; фронт в целом аккуратен, но UI разрешает действия, которые может запретить сервер (нет UX-фидбека по ошибкам).
- Техдолг (ключевое):
  1) Нет автоматических тестов и CI/CD.
  2) In-memory rate-limit, нет персистентного кэша/сессий/логов.
  3) Валидация неполная для ряда эндпоинтов (finance, notifications, часть PATCH/PUT).
  4) RBAC рассинхрон: nav на FE допускает финансы/отчёты для ролей без прав; `/accounts/:userId` выдаёт счета без проверки роли.
  5) Контракты: FE типы `User` включают `phone/avatar/location`, которых нет в схеме; возможны пустые данные/лишний UI.
  6) История задач хранит JSON-строки (seed) и фильтрует falsy; теряются значения `0/false`.
  7) В репозитории лежат `node_modules/` и сборки (`dist/`), увеличивая шум и риск случайных правок.
  8) Ошибки API отдаются как `{error}` без кодов/деталей; фронт частично не отображает ошибки (TaskDetails, файлы, статусы).
- Риски: утечки финансовых данных через неполный RBAC; нестабильность под нагрузкой (in-memory лимитер, нет ротации логов); отсутствие тестов может скрывать регрессии; файловое хранилище без антивируса и проверки контента.

## 4. Product Understanding
- Проблема: управляемые задачи с подтверждением результата и выплатами; контроль сроков и прозрачность для менеджмента.
- ЦА: небольшие и средние команды с ролями Admin/Manager/Employee/Finance/Viewer.
- Core features: аутентификация и роли; задачи с статусами и назначениями; комментарии и файлы; ревью задач с выплатой; финансы (счета/транзакции); уведомления; дашборд и отчёты.
- Лишнее/второстепенное сейчас: произвольные поля пользователя без поддержки в БД; “worker of month” и рандомная аналитика; эндпоинт `/files/raw/:filename` как дубликат скачивания; массив визуальных эффектов без бизнес-ценности.

## 5. To-Be Vision
- Концепция: «Единый контур выполнения задач с контролируемыми статусами, подтверждением и выплатой». Фокус — надёжный workflow и прозрачные деньги.
- MVP scope (оставляем): login/register, роли, задачи CRUD + статусы, комментарии/файлы, ревью → DONE + транзакция, базовый дашборд, уведомления, минимальные отчёты.
- Удалить/отложить: сырые загрузки файлов; декоривная аналитика без данных; неиспользуемые поля user; экспериментальные визуальные фичи.

## 6. Target Architecture
- Подход: модульный монолит в одном репо + общий пакет контрактов.
- Модули: `auth`, `users`, `tasks` (comments/files/history), `reviews-payments`, `finance-ledger`, `notifications`, `reports-analytics`, `dashboard`, `shared` (errors, logger, validation, auth, DTO/enum). Выделить `/packages/shared-contracts` (TS types + Zod/Prisma enums) для FE/BE.
- Потоки:
  - FE ↔ API через типизированный клиент, ошибки в едином формате `{code, message, details}`.
  - Файлы: только по attachment id, без raw filename; метаданные в БД, хранение в S3/локально с префиксом.
  - RBAC: централизованная матрица (policy) переиспользуется роутами и FE guard’ами.

## 7. AI Development Strategy
### 7.1 Типы агентов
- Code Analyzer Agent — статический анализ, поиск антипаттернов.
- Refactoring Agent — точечные правки, миграции, ввод контрактов.
- Test Agent — генерирует и исполняет unit/integration/e2e.
- Architecture Agent — дизайн модулей, схемы данных, API контракты.
- DevOps Agent — CI/CD, инфраструктура (Docker, Actions), наблюдаемость.
- Product Agent — формулирует фичи, UX-потоки, acceptance-критерии.

### 7.2 Распределение задач
| Тип задачи | Агент | Причина |
| ---------- | ----- | ------- |
| Поиск багов/долга в коде | Code Analyzer | Быстрое покрытие проблем по всему дереву исходников |
| Доработка эндпоинтов, валидация | Refactoring | Мелкие правки без смены архитектуры |
| Архитектура модулей/контрактов | Architecture | Требует целостного дизайна |
| CI/CD, Docker, observability | DevOps | Инфраструктурные изменения |
| Тесты (unit/integration/e2e) | Test | Системное покрытие и автозапуск |
| Формирование MVP и UX-критериев | Product | Баланс бизнес-ценности и объёма |

### 7.3 Pipeline работы агентов
1) Product Agent формулирует цель и acceptance-критерии фичи.
2) Architecture Agent уточняет контракт/схему/границы модуля.
3) Refactoring Agent реализует сервер/клиент изменения по контракту.
4) Code Analyzer Agent делает быструю проверку правок (lint, smells).
5) Test Agent добавляет/обновляет тесты и прогоняет их.
6) DevOps Agent обновляет CI/CD, собирает артефакты, выкатывает на стейдж.
7) Обратная связь → следующая итерация.

### 7.4 Формат задач для агентов
- Цель: что нужно получить (критерии done, бизнес-эффект).
- Вход: пути файлов, контракты/схемы, примеры запросов, ограничения данных.
- Ограничения: не ломать совместимость, покрыть тестами/валидацией, лимиты перфоманса.
- Ожидаемый результат: патч/PR, обновлённые схемы/доки, список тестов и их статус.

### 7.5 Ограничения
- Никакого полного переписывания; итеративные инкременты.
- Сохранять обратную совместимость публичных эндпоинтов, если нет миграции.
- Не ломать существующий функционал без строгой причины и тестов.

## 8. Refactoring Plan
### Этап 1 — стабилизация (1–2 недели)
- Довести RBAC: защитить `GET /accounts/:userId`, синхронизировать меню FE с серверной матрицей.
- Единый error-формат и отображение ошибок в FE (TaskDetails, файлы, статус смены).
- Закрыть «сырой» доступ к файлам по имени; оставить скачивание только по attachment id.
- Добавить express-validator к finance/notifications/role изменениям; normalize history (не терять falsy).
- Очистка репо (`node_modules`, `dist`, .gitignore), выровнять .env.example.
- Агенты: Refactoring + Code Analyzer + Test.

### Этап 2 — упрощение (3–5 недели)
- Ввести `packages/shared-contracts` (TS типы + Zod), использовать в FE/BE; генерация типов из Prisma.
- Перестроить структуру бэкенда на доменные модули (`modules/<domain>`), вынести общие middleware/utils.
- Установить централизованный RBAC policy и использовать в маршрутах и FE guard.
- Унифицировать ошибки и логгирование (request id, audit → file/console transport), вынести rate-limit в Redis или memory-store с очисткой.
- Агенты: Architecture (дизайн), Refactoring (имплементация), DevOps (Redis/конфиг), Test (контракты → тесты).

### Этап 3 — архитектура и готовность к прод (6–10 недель)
- Добавить наблюдаемость: healthchecks с зависимостями, metrics (Prometheus), структурированные логи.
- Docker-compose для FE/BE/DB; GitHub Actions: lint + tests + build + prisma migrate + docker build.
- E2E (Playwright) по основным сценариям: login → create task → move → review → payment → reports.
- Безопасность: секьюрные заголовки, лимиты загрузки, антивирус/скан по необходимости, ротация JWT secret.
- Агенты: DevOps, Test, Architecture (наблюдаемость), Refactoring.

## 9. Quality System
- Тестирование: unit (сервисы), integration (REST + тестовая БД через prisma test env), e2e (Playwright для фронта). Цель покрытия: 60%+ критические ветки.
- Статический контроль: ESLint/TypeScript strict (FE), добавить JS linter или мигрировать backend на TS постепенно; Prettier.
- CI/CD: GitHub Actions (lint → tests → build → prisma migrate diff → docker build); артефакты — FE `dist`, BE контейнер.
- Среда: `.env.example`, `docker-compose` для локали, feature flags через env.
- Код-ревью: policy с чек-листом (валидация, ошибки, логирование, тесты).

## 10. MVP Launch Plan
- Состав MVP: роли и login; задачи CRUD + статусы с валидным переходом; комментарии/файлы; ревью → DONE + транзакция; просмотр транзакций (ADMIN/FINANCE); дашборд KPI; уведомления.
- Шаги запуска: (1) финальные фиксы Этапа 1; (2) миграции/seed на стейдже; (3) e2e регресс; (4) настройка env/secret; (5) деплой Docker-compose; (6) мониторинг health/логи первые 72 часа.
- Риски: утечка счетов через RBAC, недоступность БД, превышение лимитов загрузки, несовпадение контрактов FE/BE. Митигация: тесты + feature flags + ограничение ролей, алерты по health.

## 13. Critical Issues (блокеры до запуска)
1) Доступ к счетам: `GET /accounts/:userId` требует роли ADMIN/FINANCE, но сейчас доступен всем авторизованным. Срочно добавить `roleMiddleware(['ADMIN','FINANCE'])` и покрыть тестом.
2) Отсутствие системных тестов и CI → риск невыявленных регрессий. Минимум: smoke-интеграционные тесты на auth/tasks/review/finance + GitHub Actions.
3) Ошибки/валидация: часть эндпоинтов (finance, notifications, смена ролей) не валидирует входные данные — риск проброса неверных типов и неконсистентной БД. Добавить express-validator и единый error-формат.
