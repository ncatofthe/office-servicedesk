## 2) Текущая концепция и фактическая структура

### Концепция
Проект — fullstack Task Manager:
- Backend (Express + Prisma + PostgreSQL): задачи, роли, ревью, финансы, отчёты, уведомления, файлы.
- Frontend (React + TS + Vite): дашборд, задачи/канбан, команда, ревью, финансы, отчёты.

### Фактическая структура
- Backend уже разбит по слоям (`routes` / `controllers` / `services`), но есть нарушения целостности доменной логики.
- Frontend структурно аккуратный (`pages`/`components`/`api`/`store`), но часть UX и RBAC не синхронизирована с backend-правилами.
- В корне лежат противоречивые документы/скрипты запуска (часть под SQLite/порт 5000, часть под PostgreSQL/порт 5001).

## 3) Найденные ошибки и риски

## Критичные (исправить в первую очередь)
1. `GET /api/users` падает из-за полей, которых нет в Prisma-схеме.
   - Файл: `task-manager-backend/src/controllers/user.controller.js:31,32,36`
   - Проблема: `phone`, `avatar`, `location` запрашиваются в `select`, но в `schema.prisma` этих полей нет.
   - Итог: раздел команды ломается на проде.

2. Обход бизнес-правил статусов через `PUT /tasks/:id`.
   - Файл: `task-manager-backend/src/services/task.service.js:15,139` + `task-manager-backend/src/routes/task.routes.js:62`
   - Проблема: общий `update()` разрешает менять `status` напрямую, обходя `updateStatus()` с проверкой переходов.
   - Итог: можно выставить нелегальный статус и нарушить workflow Review/Done.

3. Потенциальный runtime-crash в review.
   - Файл: `task-manager-backend/src/services/review.service.js:81,86`
   - Проблема: нет проверки, что `currentReview` найден перед `currentReview.status`.
   - Итог: 500 при неверном `reviewId`.

4. Схема и миграция расходятся (nullable `Account.userId`).
   - Файлы: `task-manager-backend/prisma/schema.prisma:162` vs `task-manager-backend/prisma/migrations/20260402123509_init/migration.sql:53`
   - Проблема: в схеме `String?`, в SQL миграции `TEXT NOT NULL`.
   - Итог: непредсказуемость при чистом разворачивании БД, ломается концепция системного счёта (`userId = null`).

5. Скрипт запуска и документация не соответствуют реальному backend.
   - Файлы: `ЗАПУСТИТЬ_ПРОЕКТ.ps1:47-51`, `ИНСТРУКЦИЯ_ПО_ЗАПУСКУ.txt:37`, `task-manager-backend/src/server.js:11-12`, `task-manager-backend/README.md:25`
   - Проблема: SQLite/5000/`CORS_ORIGIN`/`UPLOAD_MAX_SIZE` в скрипте против PostgreSQL/5001/`CORS_ORIGINS`/`MAX_UPLOAD_SIZE_MB` в коде.
   - Итог: у нового разработчика запуск не воспроизводится корректно.

## Высокий приоритет
6. Сырые файлы можно скачать по имени (слабый контроль доступа).
   - Файлы: `task-manager-backend/src/routes/file.routes.js:16`, `task-manager-backend/src/controllers/file.controller.js:139`
   - Проблема: `/api/files/raw/:filename` отдаёт файл по имени; проверка по задаче не выполняется.

7. История изменений в `task_history` хранится строками JSON и теряет falsy-значения.
   - Файл: `task-manager-backend/src/services/task.service.js:23-24`
   - Проблема: `oldValue ? JSON.stringify(...) : null` превращает `0/false/""` в `null`.

8. Несовпадение RBAC между backend и frontend меню.
   - Файл: `task-manager-frontend/src/components/Layout.tsx:14-15`
   - Проблема: `FINANCE` и `VIEWER` видят `/reports`, но backend допускает только `MANAGER|ADMIN`.

9. Validation неполная на create task.
   - Файл: `task-manager-backend/src/routes/task.routes.js:20`
   - Проблема: для `POST /tasks` нет валидации `status`, но статус принимается в сервисе.

## Средний приоритет
10. Нестабильная аналитика пользователей через `Math.random()`.
    - Файл: `task-manager-backend/src/controllers/user.controller.js:60`

11. Неполный error handling в модалке задачи.
    - Файл: `task-manager-frontend/src/components/TaskDetailsModal.tsx`
    - Проблема: `addComment/uploadFile/changeStatus` почти без обработки ошибок API.

12. Дублированная загрузка шрифта Inter.
    - Файлы: `task-manager-frontend/index.html:12`, `task-manager-frontend/src/index.css:1`

13. В репозитории лежат артефакты сборки и лишние файлы (`dist`, backup-файлы, тестовые upload-файлы).

### 4.2 Переделка структуры проекта (как сделать правильно)
Рекомендованная целевая структура:

```text
/task-manager
  /apps
    /backend
      /src
        /config
        /modules
          /auth
            auth.routes.js
            auth.controller.js
            auth.service.js
            auth.validators.js
          /users
          /tasks
          /reviews
          /finance
          /files
          /reports
          /dashboard
        /common
          /middlewares
          /errors
          /utils
          /types
        app.js
        server.js
      /prisma
    /frontend
      /src
        /app
          router.tsx
          providers.tsx
        /features
          /auth
          /tasks
          /kanban
          /team
          /reviews
          /finance
          /reports
          /dashboard
        /shared
          /api
          /ui
          /lib
          /types
  /packages
    /shared-contracts
      dto.ts
      enums.ts
      zod-schemas.ts
```

Почему это правильно:
- модульность по бизнес-доменам (а не по “техническим слоям” по всему проекту);
- общий пакет контрактов (`shared-contracts`) убирает рассинхрон enum/DTO между backend и frontend;
- проще тестировать и выпускать изменения независимо по feature.

### 4.3 Что доработать по функционалу
1. RBAC-end-to-end:
- backend policy + frontend route guards + скрытие пунктов меню в одном источнике правил.

2. Валидаторы запросов:
- вынести в `auth.validators.js`/`task.validators.js` и т.д.;
- покрыть все create/update endpoints.

3. Обработка ошибок:
- единый формат ошибок backend (`code`, `message`, `details`),
- единый `apiErrorMapper` на frontend.

4. Файлы:
- хранить метаданные строго через attachment id,
- для скачивания выдавать только `GET /api/files/:id/download`.

5. История изменений:
- хранить raw JSON в `task_history`, без `JSON.stringify`.

6. Документация:
- один canonical runbook (`README`),
- убрать дубли и устаревшие отчёты/инструкции.
