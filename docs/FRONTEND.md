## Основные маршруты UI

- `/` - портал/дашборд.
- `/tickets` - основной Freshdesk-like inbox/list.
- `/queue` - очередь/Kanban.
- `/admin` - компания и портал, папки, классификация заявок, команды и доступы, автоматизация, почта и импорт Freshdesk.
- `/team` - сотрудники, роли и отделы компании.
- `/reports` - отчёты.
- `/canned-replies` - шаблоны ответов.

Старые `/tasks` и `/kanban` сохранены как совместимые маршруты. Legacy `/reviews` старого task-manager контура не должен использоваться новыми ServiceDesk сценариями: backend `/api/reviews` отключён из runtime.

Backend `/api/reports` доступен только `ADMIN` и `VIEWER`, но раздел больше не показывается в основной продуктовой навигации.

## ServiceDesk поля

Frontend должен использовать `folderId`, `entityId`, `typeId`, `subtypeId`. Старые aliases не отправлять из UI.

## Freshdesk-like inbox

- `/tickets` теперь является основным рабочим экраном исполнителя.
- Вместо карточек по умолчанию используется плотный inbox/list с колонками:
  - номер заявки;
  - тема;
  - заявщик;
  - папка;
  - тип;
  - статус;
  - приоритет;
  - исполнитель;
  - последнее обновление;
  - канал.
- Если backend отдаёт `externalNumber` или `externalId`, старый номер Freshdesk показывается рядом с внутренним номером. Серверный поиск работает по теме, описанию, заявителю, внутреннему номеру и Freshdesk reference.
- Доступны фильтры:
  - текст;
  - статус;
  - папка;
  - тип;
  - подтип;
  - сущность;
  - исполнитель;
  - канал;
  - окно последнего обновления;
  - сортировка.
- В строке есть быстрые действия:
  - `Открыть`;
  - `Взять в работу`;
  - перевод по следующему доступному статусу.
- Список использует контракт `{ tasks, total, limit, offset }`: доступны размеры страницы `25/50/100`, диапазон записей и переходы назад/вперёд.
- Серверные фильтры, поиск, `Только мои`, канал, окно обновления и сортировки по созданию/обновлению применяются до пагинации. Полная выборка порциями по 100 загружается только для пока неподдержанных сервером тегов и сортировки по приоритету.
- Ошибки быстрых действий всегда показываются в интерфейсе. Если заявка создана, но часть вложений не загрузилась, UI сохраняет успешный результат, показывает номер заявки и список проблемных файлов, не предлагая создавать дубль.

## Управление учётными записями

- `ADMIN` создаёт сотрудников на `/team` через защищённый `POST /auth/register/admin` с ролями `ADMIN / AGENT / REQUESTER`.
- Основное действие при увольнении или временной блокировке — отключение доступа через `PATCH /users/:id/status`; история заявок и профиль сохраняются, активные токены отзываются.
- Список сотрудников показывает активный/отключённый статус и поддерживает поиск и фильтр доступа.
- Для администратора `/team` разделён на понятные вкладки `Сотрудники и роли` и `Отделы компании`, поэтому отделы не теряются под длинным списком сотрудников.
- Архивная роль `VIEWER` сохраняется у существующих пользователей и не подменяется на `AGENT` при простом открытии карточки. Новым пользователям доступны только продуктовые роли `ADMIN / AGENT / REQUESTER`.
- Login получает `/auth/config` и не показывает публичную регистрацию, когда она выключена. Logout передаёт текущий token явно, чтобы backend успел отозвать сессию.
- `/queue` оставлен как дополнительный kanban-экран, а не как основной inbox.

## Правила читаемости интерфейса

- Основные фильтры на `/tickets`: поиск, статус, папка и приоритет. Остальные фильтры спрятаны в блок `Дополнительные фильтры`, чтобы сотрудник не видел слишком много полей сразу.
- Если расширенный фильтр активен, блок остаётся видимым и прямо объясняет почему: так пользователь понимает, что список сужен дополнительным условием.
- Таблица заявок не должна создавать горизонтальный overflow всей страницы. Если колонок много, скролл должен быть только внутри таблицы.
- Карточка заявки использует широкий modal на desktop и компактный single-column вид на мобильных экранах.
- Длинные названия заявок, папок, пользователей и вкладок должны переноситься или обрезаться, но не ломать сетку.
- Админские вкладки (`/admin`) располагаются адаптивной сеткой и переносятся без скрытого горизонтального скролла.
- На ноутбучной ширине шапка использует две компактные строки: бренд и профиль остаются сверху, а вся навигация помещается отдельной строкой без обрезания.
- В бренд-блоке `companyName` показывается дополнительной строкой только когда он задан и отличается от `portalName`; default `Office ServiceDesk` не дублируется.
- Главная логика для сотрудника: `Создать заявку`, `Найти заявку`, `Открыть карточку`, `Ответить`, `Сменить статус`. Всё остальное не должно визуально спорить с этим потоком.

## Компания и портал

- Публичный `GET /servicedesk/product-settings` загружается до авторизации и безопасно брендирует Login/Register и рабочую шапку.
- Если endpoint временно недоступен, auth flow не блокируется: используются текущие fallback-подписи `ServiceDesk` / `Office ServiceDesk`.
- Первая вкладка `/admin` `Компания и портал` использует защищённые `GET/PATCH /servicedesk/admin/product-settings`.
- Форма настраивает `portalName`, `companyName`, `welcomeMessage`, `locale`, `timezone`, `defaultPriority`, `defaultFolderId`; в выборе папки показываются только активные папки.
- SMTP/IMAP, CORS, пароли, токены и прочие секреты в этой форме не хранятся и остаются server env.
- `locale` и `timezone` применяются к `document.lang`, заголовку вкладки и общим helper-функциям `formatDate` / `formatDateTime`. Несколько старых локальных форматтеров отдельных компонентов пока сохраняют `ru-RU` и будут переводиться на runtime helper постепенно.
- При открытии формы новой заявки UI явно выбирает `defaultPriority` и доступный пользователю активный `defaultFolderId`. Недоступная папка по умолчанию не подставляется.

## Notification center

- В шапке есть bell `notification-bell` с unread count.
- При клике открывается dropdown последних уведомлений:
  - `notifications-dropdown`
  - `notification-item`
  - `notification-read-all`
- Для длинного списка есть drawer `notifications-drawer`.
- Поддержаны:
  - `GET /notifications`
  - response shape `Notification[]`;
  - response shape `{ items, nextCursor }`;
  - `GET /notifications/unread-count`, если backend уже внедрил endpoint;
  - fallback на локальный подсчёт unread по `GET /notifications`, если `unread-count` ещё недоступен;
  - `PATCH /notifications/:id/read`;
  - fallback batch-mark для `Отметить всё прочитанным`, если `PATCH /notifications/read-all` ещё не существует.
- Если notifications endpoint ещё не готов, UI показывает мягкое сообщение и не ломает layout.
- Переход по уведомлению ведёт в `/tickets?taskId=...` и открывает карточку заявки.
- Для `ADMIN` email-failure уведомления могут показывать безопасную причину из `safeReason` или metadata, без stack trace.

## Freshdesk import UI

- В `/admin` есть вкладка `Импорт Freshdesk` (`admin-freshdesk-import`).
- Экран оформлен как wizard с двумя способами переноса.
- Рекомендуемый способ `Перенос напрямую из Freshdesk` проверяет серверную конфигурацию через `source-health`, позволяет выбрать дату и безопасный объём `20/50/100` заявок.
- Реальный прямой перенос заблокирован, пока администратор не выполнит успешный dry-run с теми же параметрами. Перед запуском показывается системное подтверждение с предупреждением не закрывать страницу.
- API key никогда не вводится и не отображается в браузере. При отсутствии конфигурации UI подсказывает server env `FRESHDESK_DOMAIN`, `FRESHDESK_API_KEY`, `FRESHDESK_DOWNLOAD_ATTACHMENTS_ENABLED`.
- Резервный способ читает JSON/CSV локально в браузере и отправляет records в существующий backend admin API. UI предупреждает, что обычный CSV Freshdesk может не содержать полную переписку и вложения.
- Результат показывает заявки `created/updated/skipped/errors`, а при наличии в ответе также количество комментариев, вложений и пользователей. Ошибки привязываются к строке или Freshdesk ticket id.
- История runs сохранена. Ответы массивом и `{ items }` обрабатываются безопасно.
- Если новые `source-health`/`pull` endpoint отсутствуют (`404/405/501`), прямой перенос отключается с понятным сообщением, а файловый импорт продолжает работать.
- Backend file-upload endpoint не требуется для текущего тестового запуска: UI отправляет `{ tickets, fileName }`.
- CLI/script flow дополнительно описан в `docs/FRESHDESK_IMPORT.md`.

## Временный пароль импортированного пользователя

- В `/team` администратор может открыть карточку пользователя и выбрать `Установить временный пароль`.
- Форма требует пароль и подтверждение длиной не менее 10 символов и вызывает `PATCH /users/:id/password`.
- UI явно предупреждает, что все текущие сессии пользователя будут отозваны.
- Пароль хранится только в локальном состоянии открытой формы, не логируется и очищается после успешного сохранения, отмены или закрытия карточки.

## UAT checklist для staging-показа

### Сценарий заявщика

1. Войти или зарегистрироваться как заявщик.
2. Открыть `/tickets`, нажать `Создать заявку`.
3. Заполнить только обязательные поля `Название` и `Описание`, при необходимости выбрать папку/тип/приоритет.
4. Убедиться, что новая заявка появилась в inbox, номер заявки хорошо виден.
5. Открыть карточку заявки и проверить, что видна публичная переписка, но нет внутренних заметок, технических email-полей и админских блоков.

### Сценарий исполнителя

1. Войти как исполнитель.
2. Открыть `/tickets` и найти заявку через поиск или фильтры.
3. Проверить, что в строке быстро читаются номер, тема, заявщик, папка, статус, приоритет, исполнитель, канал и последнее обновление.
4. Открыть карточку, перевести статус `Необработано` -> `В процессе`.
5. Добавить публичный комментарий и внутреннюю заметку.
6. Применить шаблон ответа как публичный комментарий.
7. Проверить, что timeline обновился, а email-переписка не показывает лишние технические детали заявщику.

### Сценарий администратора

1. Войти как администратор.
2. Проверить, что в основной навигации нет финансов и отчёты не продвигаются как главный раздел.
3. Открыть `/admin`, вкладку `Почта`.
4. Проверить summary, фильтры, health panel или мягкое сообщение `Диагностика email пока недоступна`.
5. Открыть вкладку `Импорт Freshdesk`.

### Сценарий импорта Freshdesk

1. В `/admin` -> `Импорт Freshdesk` убедиться, что серверное подключение настроено.
2. Выбрать 20 заявок и нажать `Проверить перенос`; заявки и файлы при dry-run не создаются.
3. Проверить номера, даты, комментарии, папки и план вложений.
4. Запустить пилотный перенос с теми же параметрами, затем повторить его и убедиться в отсутствии дублей.
5. Для резервного файлового режима выбрать JSON/CSV, выполнить `Проверить файл`, затем импорт.
6. Проверить последние import runs и разобрать все `PARTIAL/FAILED` ошибки.

### Сценарий email dry-run/real outbound

1. В карточке заявки применить шаблон ответа в режиме `Отправить email-ответ`.
2. Если outbound выключен, UI должен показать, что письмо не отправлено реально, а запись находится в тестовом режиме.
3. Если outbound включён, проверить появление исходящего сообщения в `Email-переписке`.
4. Администратор проверяет `/admin` -> `Почта`: статусы, ошибки, повтор отправки и диагностику.

## Automation UI

- Во вкладке `Автоматизация` на `/admin` администратор может:
  - просматривать список правил;
  - создавать, редактировать и удалять правила;
  - включать и выключать правило;
  - задавать порядок выполнения;
  - запускать безопасную проверку по внутреннему ID заявки;
  - смотреть последние запуски с фильтрами по заявке и правилу.
- Rule builder намеренно остаётся простым:
  - пустые conditions означают `не ограничивать`;
  - пустые actions означают `не менять`;
  - отдельный флаг замены исполнителей позволяет явно очистить список assignee.
- Для automation UI добавлены точечные `data-testid`:
  - `automation-rules-section`
  - `automation-rule-create`
  - `automation-rule-card-*`
  - `automation-rule-modal`
  - `automation-rule-test-task-id`
  - `automation-rule-test-run`
  - `automation-rule-test-result`
  - `automation-runs-list`

## SLA foundation

Backend foundation и frontend-компоненты SLA сохранены в коде для будущего развития, но
вкладка SLA и пустой SLA-блок в карточке скрыты из первого рабочего релиза. Это соответствует
текущему продуктовому решению: офис запускается без SLA и без обучения сотрудников
неиспользуемому функционалу.

## Folder/team permissions UX

- `/queue` скрыт для `REQUESTER`.
- Списки и очередь получают уже отфильтрованные заявки с backend.
- `GET /servicedesk/folders` для `AGENT` возвращает только его рабочие папки.
- Во вкладке команд админки можно:
  - назначать команде несколько папок;
  - добавлять и удалять участников команды;
  - отмечать тимлида и роль внутри команды.

## Internal notes UI

- В `TaskDetailsModal` комментарии и внутренние заметки показаны единым потоком.
- Каждый элемент потока имеет заметный бейдж:
  - `Публичный комментарий`
  - `Внутренняя заметка`
- `ADMIN` и `AGENT` могут выбирать тип сообщения через селектор и отправлять:
  - публичный комментарий;
  - внутреннюю заметку.
- `REQUESTER`:
  - видит только публичную переписку;
  - не видит селектор internal notes;
  - отправляет только `PUBLIC`.
- `VIEWER`:
  - видит только публичную переписку;
  - не видит форму отправки.
- Для устойчивых e2e/RTL селекторов добавлены `data-testid`:
  - `internal-note-selector`
  - `comments-list`
  - `comment-item`
  - `comment-submit`

## Canned replies UI

- Раздел `/canned-replies` доступен только `ADMIN` и `AGENT`.
- В навигации пункт называется `Шаблоны ответов`.
- Страница шаблонов поддерживает:
  - список;
  - поиск по названию, тексту и категории;
  - фильтр по категории;
  - фильтр по видимости `Все / Личные / Общие`;
  - фильтр по активности `Все / Активные / Отключённые`;
  - создание, редактирование, удаление;
  - включение и отключение шаблона.
- Для `AGENT` редактирование, удаление и переключение активности доступны только для своих шаблонов.
- В `TaskDetailsModal` для `ADMIN` и `AGENT` есть отдельный блок применения шаблонов:
  - поиск активного шаблона;
  - просмотр исходного текста;
  - редактирование итогового текста перед отправкой;
  - режимы `Добавить публичный комментарий` и `Отправить email-ответ`;
  - автоматическое обновление комментариев и task detail после применения.
- Если backend вернул `dryRun=true` для `EMAIL_REPLY`, UI показывает явное сообщение, что письмо реально не отправлено, потому что outbound email выключен.
- После `EMAIL_REPLY` в карточке автоматически обновляется блок `Email-переписка`.
- Для canned replies UI добавлены `data-testid`:
  - `canned-replies-page`
  - `canned-reply-search`
  - `canned-reply-card`
  - `canned-reply-create`
  - `canned-reply-form`
  - `canned-reply-save`
  - `canned-reply-delete`
  - `canned-reply-picker`
  - `canned-reply-apply-mode`
  - `canned-reply-body-override`
  - `canned-reply-apply`

## Timeline UI

- В `TaskDetailsModal` есть отдельный блок `История заявки`.
- История загружается через `GET /tasks/:id/timeline`.
- UI показывает:
  - loading/error/empty состояния;
  - вертикальную ленту событий;
  - дату и время в `ru-RU`;
  - автора события или `Система`, если `actor=null`;
  - title, description и безопасно отформатированную metadata.
- Timeline обновляется после:
  - добавления комментария;
  - добавления внутренней заметки;
  - применения canned reply;
  - смены статуса;
  - merge и close approval;
  - загрузки файлов.
- Для timeline добавлены `data-testid`:
  - `task-timeline`
  - `task-timeline-item`
  - `task-timeline-empty`
  - `task-timeline-error`
  - `task-timeline-refresh`

## Email-переписка и outbox

- В `TaskDetailsModal` добавлен блок `Email-переписка` (data-testid: `task-email-thread`):
  - показывает входящие и исходящие письма;
  - отображает тему, отправителя/получателя, дату, preview;
  - для `ADMIN` и `AGENT` дополнительно показывает технические поля:
    - `status`;
    - `dryRun`;
    - `attempts`;
    - `errorMessage`;
    - `nextRetryAt`.
- Для `REQUESTER` и `VIEWER` технические детали не показываются, остаётся безопасная история переписки.
- Для web-only заявок показывается пустое состояние: `По этой заявке пока нет email-переписки`.
- Блок обновляется вместе с общим refresh карточки (включая применение canned reply в режиме `EMAIL_REPLY`).
- В карточке заявки email thread визуально различает:
  - входящие письма;
  - исходящие письма;
  - `Тестовый режим` как нейтральный сервисный статус, а не как ошибку.

- На `/admin` добавлена вкладка `Email-очередь`:
  - доступна только `ADMIN` через guard страницы `/admin`;
  - поддерживает фильтры `status`, `taskId`, `limit`, кнопки `Обновить` и `Сбросить`;
  - показывает статусы `Тестовый режим`, `Отправлено`, `Ошибка`, `Ожидает повтора`;
  - поддерживает повторную отправку для `FAILED` и `RETRY_PENDING` с последующим обновлением списка.
- Верхний summary-блок показывает: `Всего в выборке`, `Отправлено`, `Ошибка`, `Ожидает повтора`, `Тестовый режим`, `Повторяемые`, `Заблокированные`.
- Вкладка включает health panel из `GET /servicedesk/admin/email-health`.
  - Если endpoint недоступен (например, ещё не внедрён на backend), UI показывает мягкое сообщение `Диагностика email пока недоступна`.
- Для e2e добавлены `data-testid`:
  - `admin-email-outbox`
  - `admin-email-outbox-summary`
  - `admin-email-health`
  - `admin-email-outbox-item`
  - `admin-email-outbox-retry`

## UX polish карточки и очереди

- `TaskDetailsModal` перестроен ближе к Freshdesk ticket details:
  - верхняя панель с номером, статусом, приоритетом, папкой и каналом;
  - слева основной поток переписки;
  - справа панель свойств заявки;
  - ниже сервисные блоки и история.
- Для `REQUESTER`/`VIEWER` скрываются agent-only элементы в карточке.
- Внутренние заметки заметно отделены от публичной переписки через отдельный бейдж и селектор типа сообщения.
- `TasksPage` теперь играет роль shared inbox:
  - больше полезной информации на экране;
  - заявки можно открывать и брать в работу прямо из списка;
  - номер заявки стал заметнее.
- В `TicketsPage` форма создания делает акцент на обязательных полях (`Название`, `Описание`), остальные поля показаны как дополнительные и необязательные.

## Product navigation

- Финансовый модуль не является частью продуктовой навигации ServiceDesk.
- Пункта `Финансы` в пользовательском меню нет.
- Smoke/e2e дополнительно проверяет, что `REQUESTER`, `VIEWER`, `AGENT` и `ADMIN` не видят финансовую навигацию как часть рабочего контура.
- Раздел `Отчёты` скрыт из основной навигации, чтобы не перегружать продуктовый контур.
- Legacy роли не должны светиться как отдельные продуктовые роли в UI:
  - `ADMIN` -> `Администратор`;
  - `AGENT` -> `Исполнитель`;
  - `REQUESTER` -> `Заявщик`.

## UX-правила

- Весь интерфейс на русском.
- Операционный стиль: плотные списки, понятные фильтры, минимум декоративности.
- Ошибки backend показывать понятным текстом.
- Любое действие с сохранением должно иметь loading/error/success состояние.
