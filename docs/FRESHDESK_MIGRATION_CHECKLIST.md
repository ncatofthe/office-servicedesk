# Чек-лист переноса из Freshdesk

Актуально на 2026-07-19.

Этот документ используется для реального переключения компании с Freshdesk на Office ServiceDesk.
Перенос считается успешным не по сообщению `SUCCESS`, а после сверки контрольных данных.

## 1. Подготовка

- Назначить ответственного администратора и согласовать окно переноса.
- Зафиксировать количество заявок, пользователей и период истории в Freshdesk.
- Проверить доступ администратора к Freshdesk API v2 и получить личный API key.
- Заполнить `FRESHDESK_DOMAIN` и `FRESHDESK_API_KEY` только в backend `.env` на сервере.
- Проверить свободное место для PostgreSQL, `UPLOADS_DIR` и двух комплектов backup.
- Создать свежий backup БД и вложений.
- Проверить архивы командами `pg_restore --list` и `tar -tzf`.

## 2. Dry-run

Сначала проверить небольшой диапазон без записи данных:

```bash
npm --workspace task-manager-backend run import:freshdesk:api -- \
  --dry-run \
  --max-tickets 20
```

Проверить в результате:

- нет ошибок авторизации и `429` без контролируемого retry;
- распознаны старые номера заявок;
- числовые статусы Freshdesk правильно сведены к трём рабочим статусам;
- найдены requester, responder, group и все conversations;
- показан план скачивания вложений, но файлы в dry-run не создаются;
- API key отсутствует в ответах, логах и UI.

## 3. Пилот 20-50 заявок

- Создать ещё один backup непосредственно перед real import.
- Импортировать не более 20-50 заявок.
- Открыть минимум пять заявок разных типов и статусов.
- Сверить тему, описание, старый номер, заявителя, исполнителя и исходные даты.
- Сверить число публичных ответов и внутренних заметок.
- Скачать по одному вложению из заявки и conversation.
- Убедиться, что импортированный email-тикет имеет канал `Email`, а portal-тикет канал `Web`.
- Повторить тот же import и убедиться, что задачи, комментарии и файлы не продублировались.

## 4. Полный перенос

- Сообщить исполнителям окно переключения.
- На время финального переноса запретить изменения в Freshdesk или зафиксировать время начала.
- Запустить полный CLI import. Для большого объёма не использовать браузерный HTTP endpoint.
- Сохранить stdout/stderr и ID записи `FreshdeskImportRun`.
- После первого прохода выполнить delta-import с `--updated-since` от времени начала окна.
- Не включать одновременно два real import процесса.

## 5. Контроль после переноса

- Сравнить ожидаемое и импортированное количество заявок.
- Проверить `created / skipped / errors / comments / attachments / users` в summary.
- Разобрать каждую ошибку `PARTIAL`, а не считать такой запуск завершённым.
- Найти несколько заявок по старому Freshdesk номеру в `/tickets`.
- Проверить права: заявитель видит только свои заявки, исполнитель только доступные папки.
- Установить временные пароли импортированным сотрудникам через `/team`.
- Проверить web-комментарий, internal note, email reply и новое входящее письмо.

## 6. Переключение

- Перенаправить корпоративный support mailbox на новый email intake.
- Оставить Freshdesk в read-only режиме минимум на одну рабочую неделю.
- Не удалять исходный Freshdesk export и логи миграции.
- Ежедневно контролировать `/health`, email outbox и свежесть backup.

## Rollback

Если обнаружена системная ошибка маппинга, остановить backend и email intake, затем восстановить
БД и `UPLOADS_DIR` из пары backup, созданной перед real import. Не пытаться вручную удалять
частично импортированные задачи из production БД.
