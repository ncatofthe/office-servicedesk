# Заявки и workflow

Актуально на 2026-04-23.

## Создание заявки

Минимально нужны `title` и `description`. Дополнительно можно указать `priority`, `folderId`, `entityId`, `typeId`, `subtypeId`, `assigneeIds`.

При создании backend автоматически назначает заявке сквозной номер. Во frontend он показывается в service-desk формате, например `#63`.

Заявка также может быть создана backend email intake из входящего письма. В этом случае title берётся из темы письма, description - из тела письма и email-метаданных, а заявитель определяется по адресу отправителя.

## Статусы

- `NEW` - новая.
- `IN_PROGRESS` - в работе.
- `DONE` - закрыта.
- `MERGED` - legacy технический статус из ранней реализации объединения. В актуальном workflow `UNION` ведётся через статус master-заявки, а child скрывается из основной очереди.

Для MVP пользовательский поток intentionally упрощён до трёх шагов:

- `Необработано`
- `В процессе`
- `Закрыто`

Администратор может вручную переоткрыть закрытую заявку и перевести её обратно в `Необработано` или `В процессе`. Для исполнителей workflow остаётся обычным: от новой к работе и затем к закрытию.

Legacy-статусы `REVIEW`, `POSTPONED`, `REWORK` в UI трактуются как `В процессе` ради совместимости со старыми данными.

## Очередь

Заявки группируются папками. Папки настраиваются администратором и должны соответствовать понятным бизнес-направлениям: IT, 1С, склад, маркетплейсы, документы, операции.

## Комментарии и вложения

Переписка ведётся внутри заявки. Вложения хранятся через backend files API. В MVP ограничения по типам/размеру минимальные, но перед промышленной эксплуатацией нужно добавить правила безопасности.

## Merge: LINK

`LINK` связывает заявки как относящиеся к одной теме. Каждая заявка остаётся самостоятельной.

## Merge: UNION

`UNION` объединяет child-заявки в master и дальше ведёт их как один рабочий блок.

- Child использует номер master-заявки в API и UI.
- При переводе master в `IN_PROGRESS` или `DONE` child автоматически следует за ним.
- Child скрывается из основной очереди и списков, чтобы не дублировать работу.
- Если открыть child напрямую, он всё равно показывает общий номер и актуальный статус master.
- История child не удаляется.

## Согласованное закрытие

Если master-заявка после `UNION` имеет несколько исполнителей, закрытие в `DONE` требует подтверждения каждого исполнителя через `POST /api/tasks/:id/close-approve`.

## Что ещё нужно

- История изменений должна быть удобно видна в UI.
- Нужны шаблоны ответов и ссылки на базу знаний.
- Нужен email threading и SMTP-ответы после базового IMAP intake.
